# 项目问题与文件系统设计

本文记录在使用Go完成多用户文件系统模拟项目时遇到的问题、解决思路，以及最终的文件系统结构设计。



## 文件系统整体设计

系统使用一个普通文件模拟虚拟磁盘，所有用户、目录、文件内容和元数据都保存在这个磁盘文件中。

为了方便跨平台运行，磁盘文件采用JSON格式保存。这样Windows、macOS、Linux下都可以使用同一套读写逻辑，不依赖系统特有的二进制结构或Python序列化格式。

整体结构如下：

```txt
fms.pfs
    |
    |-- format_version
    |-- users
    |       |-- root
    |       |-- 普通用户
    |
    |-- nodes
            |-- base
                    |-- root
                    |-- home
                    |       |-- user01
                    |       |-- user02
                    |
                    |-- etc
```

其中每一个目录和文件都被抽象成一个Node。

Node中保存以下信息：

1. ID：节点编号，用于在磁盘中唯一定位节点
2. Name：文件或目录名称
3. Type：节点类型，分为file和dir
4. Parent：父目录ID
5. OwnerID：所属用户ID
6. Children：目录下的子节点
7. Content：文件内容
8. Created、Modified、Accessed：创建、修改、访问时间



## 模块拆分

最开始实现时，所有逻辑放在一个入口文件中，调试比较方便，但是代码变长以后会出现几个问题：

1. 命令解析、磁盘读写、路径解析、权限判断混在一起
2. 新增命令时不容易判断应该修改哪里
3. 测试内部逻辑时需要绕过命令行入口
4. 后续维护时容易出现重复代码

因此将程序拆成以下文件：

```txt
cmd/pfs/main.go
internal/pfs/app.go
internal/pfs/types.go
internal/pfs/disk.go
internal/pfs/session.go
internal/pfs/commands.go
internal/pfs/path.go
internal/pfs/terminal.go
```

各文件职责如下：

1. `cmd/pfs/main.go` 只负责程序入口
2. `app.go` 负责处理 `init`、`run`、`help` 等外层命令
3. `types.go` 定义User、Node、Disk、Session等核心结构
4. `disk.go` 负责磁盘初始化、读写和格式恢复
5. `session.go` 负责交互循环、登录、用户切换和命令分发
6. `commands.go` 负责实现文件系统命令
7. `path.go` 负责路径解析、当前目录、权限检查
8. `terminal.go` 负责跨平台终端操作

这样拆分后，命令逻辑和底层存储逻辑互相分离，后续扩展比较清楚。



## 磁盘初始化问题

项目需要先生成虚拟磁盘文件，再进入文件系统。

初始化时主要做三件事：

1. 创建root用户
2. 创建根节点base
3. 创建初始目录root、home、etc

初始化后的默认用户为：

```txt
username: root
password: root
```

遇到的问题是，如果用户直接运行文件系统而没有先初始化磁盘，程序会找不到 `fms.pfs`。

最开始的做法是在入口处明确区分两个命令：

```bash
pfs init
pfs run
```

后来为了让直接运行更自然，入口又做了调整：

1. 不带参数时默认等价于 `pfs run`
2. 如果磁盘不存在，则自动初始化 `fms.pfs`
3. 初始化完成后直接进入登录流程

这样保留了 `init` 和 `run` 的显式控制，同时也支持“直接点运行就进系统”。

同时为了方便直接启动，项目还提供了 `launch.sh`，默认通过 `go run ./cmd/pfs` 运行当前源码版本。



## JSON目录恢复问题

使用JSON保存磁盘时，空目录的Children字段可能不会写入文件。

例如一个空目录保存后可能只剩：

```json
{
  "id": "5",
  "name": "demo",
  "type": "dir"
}
```

再次读取时，如果直接向Children中添加新文件，就可能出现空map写入错误。

解决方法是在加载磁盘后统一执行一次恢复：

1. 遍历所有节点
2. 如果节点类型是dir
3. 如果Children为空，则重新创建一个空map

这样可以保证目录节点在内存中始终可写。



## 路径解析问题

虚拟文件系统有自己的路径规则，不能直接使用操作系统路径。

例如Windows使用反斜杠：

```txt
C:\Users\demo
```

而虚拟文件系统统一使用斜杠：

```txt
/home/user01/demo
```

如果直接使用系统路径规则，Windows、macOS、Linux下的行为可能不一致。

解决方法是让虚拟文件系统内部固定使用 `/` 作为路径分隔符。

路径解析时支持：

1. `/` 从base根目录开始
2. `~` 从base根目录开始
3. `..` 返回上级目录
4. `.` 表示当前目录
5. 普通名称表示进入子目录或访问子文件

这样系统路径和虚拟路径互不影响。



## 权限控制问题

文件系统需要支持多用户，因此不能让所有用户都能修改所有目录和文件。

当前采用较简单的权限模型：

1. root用户可以读取和修改所有节点
2. 普通用户可以读取和修改自己拥有的节点
3. home和etc这类公共目录允许普通用户读取
4. 普通用户不能修改其他用户目录下的内容

权限判断统一放在两个函数中：

1. canRead
2. canWrite

这样命令实现时只需要调用权限函数，而不用在每个命令中重复写判断逻辑。



## 跨平台清屏问题

Windows清屏命令是：

```bash
cls
```

macOS和Linux清屏命令是：

```bash
clear
```

如果写死其中一个命令，就会导致另一个平台不可用。

解决方法是在运行时判断系统类型：

1. Windows下执行 `cmd /c cls`
2. 其他系统下执行 `clear`

清屏功能属于辅助功能，即使执行失败也不影响文件系统继续运行。



## 命令实现问题

文件系统需要支持常见的目录和文件操作。

主要命令如下：

```txt
useradd [name]          添加用户
su username             切换用户
passwd [username]       修改密码
pwd                     显示当前路径
mkdir name              新建目录
touch name              新建文件
vim name [content...]   写入文件内容
more name               查看文件内容
cd path                 切换目录
cp src target_dir       复制文件
mv src target_dir       移动文件或目录
rename old new          重命名
tree [-d depth]         默认递归显示全部，`-d` 可限制层数
ls                      显示目录内容
ll                      显示目录详细信息
stat name               显示节点元数据
detail                  显示磁盘概览
rm [-r] name            删除文件或目录
exit                    保存并退出
```

实现命令时遇到的主要问题是：不同命令都会用到路径解析、权限判断、节点查找、时间更新。

解决方法是把公共逻辑抽出来：

1. resolve负责根据路径找到节点
2. cwd负责获取当前目录
3. sortedChildren负责排序目录内容
4. markChanged负责更新时间
5. removeSubtree负责递归删除目录

这样每个命令只关注自己的业务逻辑。



## 数据保存问题

交互式文件系统不能只在内存中修改数据，否则退出后文件会丢失。

解决方案是在每次命令执行后保存磁盘：

1. 用户输入命令
2. 执行命令并修改内存中的Disk结构
3. 将Disk重新写回 `fms.pfs`

这样即使用户没有显式保存，只要命令执行完成，数据就已经同步到磁盘文件。

退出系统时也会再保存一次，避免最后一次操作丢失。



## 测试问题

交互式程序不容易测试，因为它依赖用户输入。

解决方法是分成两种测试：

1. 单元测试：直接构造Disk和Session，测试路径解析、目录创建、初始化结构
2. 冒烟测试：使用管道模拟用户输入，检查程序能否完成一次完整流程

例如：

```bash
go test ./...
```

也可以模拟一次运行：

```bash
printf 'root\nroot\nmkdir demo\ncd demo\nvim note hello\nmore note\nexit\n' | go run ./cmd/pfs run
```



## 构建产物问题

Go项目编译后会生成可执行文件。

不同平台下产物名称可能不同：

```txt
pfs
pfs.exe
```

同时运行时会生成虚拟磁盘文件：

```txt
fms.pfs
```

这些文件不应该提交到仓库。

解决方法是在 `.gitignore` 中忽略：

```txt
fms.pfs
/pfs
/pfs.exe
```

如果使用IDE，还需要忽略IDE配置目录，避免把本地环境配置提交上去。



## 最终设计总结

这个文件系统的核心思路是：

1. 用一个磁盘文件保存完整文件系统状态
2. 用Node统一表示目录和文件
3. 用User表示用户和密码信息
4. 用Session表示一次交互登录状态
5. 用路径解析函数把用户输入转换为节点
6. 用权限函数控制不同用户的访问范围
7. 用JSON保证多平台读写一致

相比直接依赖操作系统文件目录，这种方式更适合课程设计中的文件系统模拟，因为所有目录、文件、用户、权限和元数据都由程序自己管理。
