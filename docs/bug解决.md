# 遇到的一些有价值的bug

记录实现过程中遇到的典型问题。


## JSON 反序列化后空目录无法写入

最早把虚拟磁盘保存成 JSON 以后，发现重新加载磁盘时，某些空目录在后续 `mkdir` 或 `touch` 时会报错。

原因是空目录的 `Children` 在 JSON 中可能被省略，读取回来以后就是 `nil`，后面再向里面写子节点时就会失败。

解决方法：

1. 加载磁盘后统一执行 `normalize`
2. 遍历所有节点
3. 如果节点类型是目录并且 `Children == nil`
4. 则补一个空 map

这样目录节点在内存中总是可写的。



## 默认启动时参数被当成未知命令

项目后来支持“不带参数默认运行”，一开始只处理了完全没有参数的情况。

结果像下面这种写法：

```bash
./launch.sh -disk /tmp/demo.pfs
```

会把 `-disk` 当成未知子命令。

解决方法：

1. 在入口先判断第一个参数是否以 `-` 开头
2. 如果是，则直接按 `run` 模式解析这些参数

这样无参数启动和带 `run` 参数的默认启动都能成立。



## 登录密码错误后的交互不友好

最开始密码输错会直接退出进程，用户必须重新启动程序。

后来改成只提示错误并允许继续输入密码，但又出现另一个问题：用户名输错时只会打印 `user not found`，交互不一致。

解决方法：

1. 把启动登录改成单独的交互流程
2. 密码错误后允许：
   `retry password / back to username / exit`
3. 用户名不存在后允许：
   `back to username / exit`
4. `su` 仍然保留单次失败返回，避免命令行卡住

这样启动登录更符合实际使用习惯。



## launch.sh 复用旧二进制导致行为和源码不一致

为了加一键启动脚本，最开始 `launch.sh` 会优先执行当前目录已有的 `./pfs`。

问题是如果源码已经改了，但 `./pfs` 还是旧版本，用户会看到“代码明明改了，运行结果却没变”。

这个问题在验证 `passwd` 时就出现过。

解决思路：

1. 运行前要明确知道自己是在执行源码还是旧二进制
2. 调试阶段优先使用 `go run ./cmd/pfs`
3. 如果保留优先执行 `./pfs` 的逻辑，测试时要注意区分

这个问题本身不是文件系统逻辑错误，但很容易误导排查方向。
